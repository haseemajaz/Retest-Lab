## v0.25.0: per-setup outcomes, and a ladder you can see at scale

A trace is a flat list of bars; now it reads setup by setup. `python -m reference.ledger trace.csv` builds a per-setup ledger from a reference trace: each setup's armed bar, end bar, bars held, fill bar, targets hit, and outcome — `all_targets`, `stop`, `cancelled` (with the reason: `expired`, `outside_session`, `day_rollover`, `stop_before_fill`), or `open`. Ambiguous bars are counted on the setup they belong to, so a flagged outcome is never silently folded into an outcome. The audit report gains a "Setup outcomes" section with the same table and counts. Try it: `python -m reference.engine sample_ledger.csv --output sample_ledger_trace.csv` then `python -m reference.ledger sample_ledger_trace.csv` — three setups: one reaches all targets, one stops after target 1, one expires unfilled. See SETUP_LEDGER.md. The ledger calculates no win rate, return, or profitability; it counts modeled threshold events only.

Two visual improvements. The calculator's price ladder is now drawn to scale: `ladder.js` gains `geometry()`, which positions each level by actual price distance (0 at the highest price, 100 at the lowest), and `calculator.html` renders it as an SVG chart beside the level table — a wide gap on the chart is a wide price distance, even for a one-tick setup. The trace viewer's rejection breakdown now draws a bar per reason, sized by its share of rejected bars (`barWidth()` in `trace_viewer.js`).

## v0.24.0: rejection reasons you can actually see — and only where they apply

Two things changed about `reject_reason`. First, its meaning: in v0.23.0 a candidate diagnosis was recorded regardless of engine state, so a bar could show both `modeled_fill` and `reject_reason` `warmup` — it read as if the bar itself had been rejected while it filled or hit targets. In v0.24.0 a reason is recorded only on a bar that started idle and did not arm, because arming is only attempted from idle. Traces generated by v0.23.0 and v0.24.0 therefore differ on armed/active bars (the reason is now blank there); idle-bar reasons are unchanged. Try it: `python -m reference.engine sample_trace.csv` — the fill and target bars no longer carry `warmup` — while `python -m reference.engine sample_reject.csv` still shows bar 20 `weak_body`, bar 21 `close_edge`, bar 22 `no_breakout`, bar 23 arms long.

Second, the reason is now visible where you look for it. The trace viewer shows a per-reason breakdown (reason, bar count, share of rejected bars) with visible rejected-bar and ambiguous-bar counts, and the row filter gains Rejected bars and Ambiguous bars alongside All bars and Bars with events. The audit report's modelled timeline gains a Reject reason column, and its Ambiguity & rejection section now states the rejected-while-idle count and the most common reason. The embedded viewer sample is generated from the current engine output, so it can no longer disagree with the engine.

## v0.22.0: intrabar order ambiguity, flagged not fixed

An OHLC bar records a range, not the order prices were visited inside it. The trace now adds an `order_ambiguity` column that flags bars where one range spans levels whose order decides the modelled outcome, instead of letting the row read as an observed sequence. Labels: `fill_vs_stop` (armed bar spanned entry and stop; model cancels, stop first), `fill_vs_target` (fill bar also spanned a target; model records no target on a fill bar), `stop_vs_target` (active bar spanned stop and an unhit target; model records stop only), `target_order` (two or more unhit targets spanned on one active bar). Already-hit targets do not count again, and day/session/expiry cancellations are not flagged as price-order cases, because price order did not decide those outcomes.

Try the synthetic samples: `python -m reference.engine sample_order_ambiguity.csv` (bar 22: `stop`, `stop_vs_target|target_order`) and `python -m reference.engine sample_order_ambiguity_fill.csv` (bar 21: `modeled_fill`, `fill_vs_target`, no targets recorded). The trace viewer counts ambiguous bars and shows the label beside the events; the audit report adds an Order ambiguity column and a count; the comparator accepts `order_ambiguity` as a recorded field. Open `ORDER_AMBIGUITY.html` for the visual guide with the same bar read two ways.

The flag changes no event, level or outcome: the stop-first and fill-bar conventions are unchanged from v0.21.0. A flagged bar is not a win or a loss — treat it as "needs finer data" (tick data or a smaller timeframe) and do not use flagged bars to estimate a win rate. A trace with no flagged bars is not proof of a clean sequence.

Input CSV headers required: `index,day,open,high,low,close,prior_high,prior_low,prior_atr`. `index` must be consecutive, nonnegative bar indexes. `day` is YYYY-MM-DD in the indicator's selected timezone. Optional columns: ISO `timestamp` (copied into trace), `ema`, `volume`, `prior_volume_avg`, `vwap`, `in_session`, `confirmed`. Session and confirmed default to true; a false confirmed value is rejected. Volume and averages must match the feed. Blank filter inputs fail that filter. The tool starts idle, so include enough preceding history and do not assume its initial state matches a chart that already has a setup. The tool does not calculate ATR, EMA, VWAP, sessions or market data. Compare same bars, settings, session timezone and tick size, then document any mismatch. Do not treat agreement as independent Pine validation or proof of returns.

## Indicator features (v0.3.0)
- Optional minimum breakout distance as a multiple of previous-bar ATR (default 0, preserving the earlier breakout rule).
- Optional retest-side close confirmation (default OFF). A bar must span entry and close at or above entry for longs, at or below for shorts. The model records the touched level retrospectively at bar close, not an executable fill or guaranteed price.
- Optional session VWAP direction filter (default OFF): confirmed breakout close strictly above/below TradingView's built-in `ta.vwap(hlc3)`. Missing VWAP fails the filter. This is an independent interpretation, not the creator’s implementation. Feed volume, session/anchor and timeframe affect it; especially evaluate on intraday standard candles. EMA and prior relative-volume filters remain available, also off by default. All enabled filters must pass.
- Cancel reason, last-event dashboard, optional markers/levels, and long/short-specific named alerts. JSON schema is now `retest_lab.v3` with `cancel_reason` string or null; recreate all alerts when changing source or inputs.

## Rules in brief
On a confirmed breakout bar, close strictly breaks the preceding 20-bar high/low; candle body >= 0.8 prior ATR and close lies in the outer 25% of the bar. Optional breakout distance is measured beyond the boundary in prior ATR. Entry is the tick-rounded broken boundary; stop is the breakout extreme plus a 0.1 prior-ATR buffer. Require valid tick geometry and risk between 0.25 and 3.0 prior ATR. Arm for up to 10 subsequent bars. Pending cancellation precedence: calendar-day rollover, out of session, expiry, stop breached. Otherwise entry must be spanned; optional close confirmation further restricts it. Gaps that do not span entry are not modeled fills. No target is recorded on the fill bar because OHLC cannot order events. On later bars stop wins over targets, and 0.6R/1R/1.5R/2R thresholds are recorded once. T4 ends the model. Cooldown: 5 full bars after termination; cap: 3 modeled fills/calendar day. Pending setups cancel at session/day boundaries, active setups persist. These threshold observations are not orders or P&L; gaps and partial exits are not execution simulations.
